TASK: In our repo people often have `vite` running in one terminal and `vite build --watch` in another. Sometimes they also start a second `vite --mode staging` or `vite --port 3001`. Where does it keep track of running processes, and what happens if a dev server crashed and left that state behind?
KEY: 1) Only the CLI commands take process locks: `vite` (dev/serve), `vite build` and `vite preview`. cli.ts adds commandLockPlugin to dev and preview and calls createCommandLock for build. The JS API (createServer/build/preview called directly) neither creates nor checks locks, so the e2e createServer() is never blocked and never blocks anyone. `vite optimize` does not lock either. 2) A conflict happens only when the command type (dev, build or preview), the resolved project root, the config file and the mode are all the same (isSameCommand). So `vite` plus `vite build --watch` is fine (different command), and `vite` plus `vite --mode staging` is fine (different mode). A second plain `vite` with the same root, config and mode is refused, even with a different --port, because the port is not part of the match. The refusal is the error "Found another Vite dev process for this project at <url> (PID <pid>). Pass --bypass-lock to bypass this check.", after which the CLI exits with code 1. --bypass-lock is a global flag that turns off both writing and checking locks for that process. 3) Lock files are JSON records (command, root, configFile, mode, pid, startTime, urls) in the `lock` subdirectory of cacheDir, so by default node_modules/.vite/lock/<hash>.json, or .vite/lock when there is no package.json. The cacheDir default comes from the shared-options doc and the subdirectory from the CLI doc's process-locks section. 4) Stale state: when scanning, a lock whose PID is no longer alive is deleted and ignored. If the PID is alive but the recorded process start time differs from the actual one (PID reuse after a crash or reboot), the lock is also deleted. Only a live process with a matching start time blocks. Locks are removed on normal exit and SIGINT (and SIGTERM for build), and on server close.

=== ITEM g09 (httpx q3, question)
TASK: We're migrating from requests. One upstream API sends Content-Type: text/plain with no charset, and the body is really Windows-1252. With requests .text looked fine; with httpx we get replacement characters. The compatibility guide says httpx guesses the encoding with charset_normalizer, so what's going on? KEY: HTTPX does not auto-detect encodings by default: when the Content-Type has no (known) charset it uses the client's default_encoding, which defaults to 'utf-8', and decodes with errors='replace', hence U+FFFD characters. The compatibility guide's 'Content encoding' paragraph (charset_normalizer guessing) is stale -- charset_normalizer is not a dependency in pyproject.toml and the code (Response.encoding) just uses default_encoding; the Text Encodings guide is the accurate doc. Fixes: set httpx.Client(default_encoding='cp1252') (or 'windows-1252'), or pass a callable for autodetection (e.g. using chardet or charset-normalizer, which must be installed separately) -- default_encoding is a Client/AsyncClient (and Response) option, not a top-level httpx.get() argument; per-response you can set r.encoding = 'cp1252' but only before .text is accessed (afterwards it raises ValueError). KEY: 1) The shortest config is future: 'warn'. UserConfig types future as FutureOptions | 'warn', and resolveConfig expands the string into all flags set to 'warn' (checked with `satisfies Required<FutureOptions>`). The docs for the future option (shared-options.md) only describe a record of flag names and never mention the string shorthand, so an answer that only lists the individual flags is not the least config. 2) There are exactly nine flags in FutureOptions: removePluginHookSsrArgument (a plugin reads options.ssr in resolveId/load/transform, in dev and in build), removePluginHookHandleHotUpdate (a plugin that has handleHotUpdate and no hotUpdate runs on a file 'update'), removeServerModuleGraph, removeServerReloadModule, removeServerPluginContainer, removeServerHot, removeServerTransformRequest, removeServerWarmupRequest (each fires when the matching ViteDevServer getter or method is used), and removeSsrLoadModule. removeSsrLoadModule fires for server.ssrLoadModule and also for server.ssrFixStacktrace and server.ssrRewriteStacktrace. Each warning is printed once (warnOnce), prefixed '[vite future]', with a link to vite.dev/changes/<page> (this-environment-in-hooks, hotupdate-hook, per-environment-apis or ssr-using-modulerunner) and usually a stack trace. 3) 'Shared plugins during build' (builder.sharedConfigBuild) is listed on the breaking-changes page but has no future flag and gives no warning. 4) server.hot replacement: docs/changes/per-environment-apis.md says `server.hot -> server.client.environment.hot`.
